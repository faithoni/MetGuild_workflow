# MetGuild Workflow

**Release candidate: `0.1.0-rc.1`** — prepared for validation, not a stable release. The canonical version is in [VERSION](VERSION). See [release notes](Releases.md) and the [release acceptance checklist](RELEASE_CHECKLIST.md) for tested scope and outstanding checks.

A reproducible downstream workflow for defining metabolic potential guilds from functionally annotated, genome-centric metagenomic data.

MetGuild cleans genome-by-feature matrices, selects candidate cluster counts, performs clustering and statistical screening, computes correlations, and exports network edge lists, node attributes, a populated provenance database, and an interactive HTML workflow map.

The code implements Phases I and II. Phase III—the interpretation of network modules as metabolic potential guilds—requires expert knowledge.

This repository accompanies the manuscript by **Faith I. Oni and Ulisses N. Rocha (2026)**, *MetGuild: A Genome-Resolved Workflow for Identifying Metabolic Potential Guilds: Application to a Long-Term Sulfate-Reducing Benzene-Degrading Consortium*. The existing manuscript information lists *Ecological Informatics*; the final citation and DOI remain to be supplied.

## Scope

MetGuild starts from genome-level functional annotation matrices generated by external tools. At least one matrix is required; multiple datasets can be analyzed independently.

The repository does not perform raw-read processing, genome recovery, taxonomic classification, genome annotation, or metabolic model reconstruction. Taxonomy is supplied as an optional annotation table. Network files can be used for downstream visualization and module analysis.

## Installation

Use a Bash-capable environment with Conda. The dependency specification requires Python **3.10–3.13** and includes NumPy, pandas, SciPy, scikit-learn, Matplotlib, and Plotly.

```bash
git clone https://github.com/faithoni/MetGuild_workflow.git
cd MetGuild_workflow
conda env create -f environment.yml
conda activate metguild_workflow
```

Activate the environment in each new shell before running MetGuild. The runner checks dependencies but does not activate Conda itself. Running the script through `bash` does not require `chmod +x`.

## Quick start

Run the bundled examples from the repository directory after activating the Conda environment.

Binary presence/absence data, with taxonomy:

```bash
bash run_metguild_workflow.sh Example_dataset/binary_matrix.csv 15 \
  --matrix-type binary \
  --taxonomy Example_taxonomy.csv
```

Proportional data in the interval [0, 1], with taxonomy:

```bash
bash run_metguild_workflow.sh Example_dataset/proportional_matrix.tsv 15 \
  --matrix-type proportion \
  --taxonomy Example_taxonomy.csv
```

Each command runs all stages, including the SQLite, SQL, and HTML provenance exports. Omit `--taxonomy Example_taxonomy.csv` to run without taxonomy annotation.

For your own data, replace the matrix and taxonomy paths with matching files. For example:

```bash
bash run_metguild_workflow.sh data/my_dataset.tsv 15 \
  --matrix-type binary \
  --taxonomy data/my_taxonomy.csv
```

The workflow is non-interactive. Step 4 selects chi-square for binary matrices and ANOVA for proportional matrices from the recorded matrix type, not the input filename.

Absolute paths are supported. Relative input, taxonomy, and output-directory paths are resolved from the directory containing `run_metguild_workflow.sh`.

## Input requirements

### Functional matrix

Provide a UTF-8 CSV or TSV file with:

- One column named exactly `Genomes`, containing nonempty, unique genome/sample identifiers.
- One or more numeric feature columns representing genes, pathways, modules, reactions, or other functional measurements.
- Unique, nonempty column names without surrounding whitespace. `Cluster` is reserved for workflow output.

Example binary CSV:

```csv
Genomes,gene_A,gene_B,pathway_C
MAG001,1,0,1
MAG002,1,1,0
MAG003,0,1,1
MAG004,0,0,1
```

This illustrates the format; useful clustering and statistical screening require an appropriate dataset size and variation.

| Matrix type | Accepted values | Default distance | Step 4 test |
|---|---|---|---|
| `binary` | Exact 0/1 values | Jaccard | Pearson chi-square |
| `proportion` | Numeric values in [0, 1] | Ruzicka | One-way ANOVA |

Use `--matrix-type proportion` explicitly for proportional data. The default `auto` detects exact binary data; other values are classified as quantitative, which the runner does not accept beyond Step 1.

Step 1 removes all-zero and all-missing feature columns. Partially missing feature values cause an error by default; `--missing-values zero` explicitly replaces them with zero. Missing feature markers include empty cells, `NA`, `NaN`, `N/A`, `null`, and `none`, case-insensitively.

Genome identifiers such as `NA`, `NULL`, and `001` are preserved as strings. Feature names, including numeric-looking names such as `001`, are preserved in network exports. Avoid feature names that exactly match generated final cluster-node names, such as `C1_KM3`, because those names would collide.

### Optional taxonomy

Supply `--taxonomy FILE` with a table containing `Genomes` and exactly one of `Phyla` or `Phylum`:

```csv
Genomes,Phyla
MAG001,Bacteroidota
MAG002,Desulfobacterota
MAG003,Chloroflexota
MAG004,Hadarchaeota
```

Comma-, tab-, and whitespace-delimited tables are accepted. Provide one row per genome and nonempty phylum assignments matching the input genomes. The bundled `Example_taxonomy.csv` matches the example matrices. For your own dataset, supply a taxonomy table with matching genome identifiers.

Taxonomy annotates existing clusters; it does not influence clustering. Step 3b writes a `MAG_Phyla` field containing semicolon-separated genome–phylum pairs, which Step 8 carries into cluster node attributes.

## Command-line options

```text
bash run_metguild_workflow.sh <input_matrix> [MAX_K] [OPTIONS]
```

`MAX_K` defaults to 15 and is an **exclusive** upper bound: candidate counts are 2 through 14, subject to dataset-size and valid-clustering constraints.

| Option | Default / behavior |
|---|---|
| `--matrix-type auto\|binary\|proportion` | `auto`; specify the intended type for full runs |
| `--full` | Run Steps 1–9; already the default |
| `--step1-only` | Stop after matrix preparation and candidate-k selection |
| `--clustering-only` | Stop after clustering and optional taxonomy annotation |
| `--through-step4` | Stop after statistical screening |
| `--output-dir PATH` | Choose a fresh output directory |
| `--taxonomy FILE` | Enable taxonomy annotation |
| `--input-format auto\|csv\|tsv` | `auto` |
| `--distance auto\|jaccard\|ruzicka\|euclidean` | `auto`, selected from matrix type |
| `--candidate-source union\|kmeans` | `union` |
| `--mds-components N` | 3 |
| `--n-init N` | 100 KMeans initializations |
| `--kmeans-max-iter N` | 100 |
| `--random-state N` | 0 |
| `--missing-values error\|zero` | `error` |
| `-h`, `--help` | Display usage |

Choose at most one stop option; do not combine a stop option with `--full`.

For example, to stop after statistical screening:

```bash
bash run_metguild_workflow.sh data/my_dataset.tsv 15 \
  --matrix-type binary --through-step4
```

The runner uses the downstream scripts' default statistical thresholds. For stage-specific options, inspect the corresponding script's `--help`; those options are not automatically forwarded by the runner.

## Workflow stages

All scripts below are in `scripts/`, except the Step 9 implementation embedded in the runner.

| Step | Script | Behavior |
|---|---|---|
| 1 | `01_removing_zero_columns_K_Optimization.py` | Clean the matrix, compute dissimilarities and classical MDS, and select candidate k values |
| 2 | `02_kmeans_mds_clustering.py` | KMeans on saved classical-MDS coordinates |
| 3 | `03_hierarchical_clustering.py` | Average-linkage clustering on the original dissimilarities |
| 3b | `03b_taxonomy_annotation.py` | Optional cluster taxonomy annotation |
| 4 | `04_statistical_testing.py` | Chi-square or ANOVA screening with Benjamini–Hochberg correction |
| 5 | `05_feature_feature_correlation.py` | Feature–feature Spearman correlations |
| 6 | `06_feature_cluster_correlation.py` | One-vs-rest feature–cluster Spearman associations |
| 7 | `07_cluster_cluster_correlation.py` | Spearman correlations between cluster profiles |
| 8 | `08_merge_filtered_files.py` | Merge retained edges and create node attributes |
| 9 | Embedded in `run_metguild_workflow.sh` | Build the SQLite provenance database, SQL reconstruction dump, and HTML workflow map |

By default, candidate k values are the unique union of four KMeans selections (elbow/inertia, silhouette, Calinski–Harabasz, and Davies–Bouldin) and the hierarchical silhouette selection. `--candidate-source kmeans` uses the KMeans selections only.

Step 7 represents binary matrices as cluster-wise feature prevalence and proportional matrices as cluster-wise mean feature values.

### Statistical and network defaults

- Step 4 retains features using BH-adjusted p < 0.05 within each clustering solution.
- Step 5 retains feature–feature associations with |rho| >= 0.5 and BH-adjusted p < 0.05.
- Steps 6 and 7 retain positive associations with rho >= 0.5 and BH-adjusted p < 0.05 by default.
- Perfect correlations (|rho| approximately 1, within the code's tolerance) are excluded from retained network edges.
- Correlation outputs use cluster names `C1`, `C2`, etc. Final network names identify the method and k, for example `C1_KM3` and `C1_HC3`.
- A feature named `C1` remains distinct from a final cluster node such as `C1_KM3`.

Treat the results as exploratory association screening. Correction is performed within each clustering solution and does not account for selection induced by earlier clustering and feature screening. Sparse chi-square tables are flagged but not excluded by default; the standalone Step 4 script offers `--require-expected-ge5`. Review diagnostic outputs and statistical assumptions when interpreting results.

## Outputs and provenance

For `my_dataset.tsv`, the runner creates `my_dataset_run_01/` under the workflow directory. Later runs use `_run_02`, `_run_03`, etc. Use `--output-dir` to select another fresh directory.

A complete run is organized as follows:

```text
my_dataset_run_01/
├── my_dataset.tsv
├── my_dataset_cleaned.tsv
├── scripts/
├── inputs/                         # taxonomy input, when supplied
├── manifests/
│   └── optimal_k_values.json
├── 02_k_optimization/
├── 03_04_clustering/
│   ├── 01_kmeans/
│   ├── 02_hierarchical/
│   └── taxonomy/                   # when supplied
├── 05_stat_analysis/
├── 06_correlation/
│   ├── 01_featurevsfeature_correlation/
│   ├── 02_featurevscluster_correlation/
│   └── 03_clustervscluster_correlation/
├── 07_network_construction/
│   ├── edge_lists/
│   ├── nodes_attributes/
│   ├── 01_edge_list_merge_summary.csv
│   └── network_construction_manifest.json
└── 08_workflow_provenance/
    ├── my_dataset_workflow_provenance.db
    ├── my_dataset_workflow_provenance.sql
    └── my_dataset_workflow_provenance.html
```

For a KMeans solution with k=3, network filenames include:

- `edge_lists/my_dataset_cleaned_3_KM_edge_list.csv`
- `nodes_attributes/my_dataset_cleaned_3_KM_node_attributes.csv`

Edge tables contain `node1`, `node2`, signed `weight`, `abs_weight`, nonnegative `mcl_weight`, `p_value`, `adjusted_p_value`, and `edge_type`. Node tables contain `Node`, `Group`, `Original_Name`, `Method`, `K`, and `MAG_Phyla`.

Before Step 9, the runner validates the network manifest, summary, edge lists, node tables, and reported row counts. Individual solutions may be empty, but the full run must contain at least one retained edge and a populated node table. If every solution has zero retained edges, the runner stops before the SQLite/SQL/HTML export; inspect the statistical and correlation summaries to understand the empty result.

Manifests record parameters, software versions, paths, and SHA-256 fingerprints. These support provenance and consistency checks; they are not digital signatures. Step 9 imports scientific CSV/TSV/JSON artifacts into a local SQLite database, produces a SQL dump that can recreate it, and generates a browser-based workflow map.

MetGuild runs locally and does not require application logins, API keys, or access tokens. Access to repository downloads and local files is handled separately by GitHub and the operating system.

### HTML workflow map

The HTML report is the main human-facing view of the run's scientific results. It is generated automatically in Step 9; no extra flag or web server is required.

After the first binary example run, open:

```text
binary_matrix_run_01/08_workflow_provenance/binary_matrix_workflow_provenance.html
```

For the proportional example:

```text
proportional_matrix_run_01/08_workflow_provenance/proportional_matrix_workflow_provenance.html
```

Double-click the HTML file in your file manager or open it from your browser. Use the actual run directory printed by the launcher: subsequent runs use `_run_02`, `_run_03`, etc., and `--output-dir` changes the location.

The map supports:

- Searching by filename, path, method, or result type.
- Filtering by workflow step, result type, clustering method, and candidate k.
- Selecting a result node to inspect its upstream/downstream links, file path, checksum, dimensions, and preview.
- Previewing tables (up to 30 rows and 80 columns) and figures, and opening original result files or interactive plots.
- Zooming the graph to explore its connections.

The map shows original sources, main scientific figures, tables used by later analysis stages, and final network tables. Diagnostic matrices, summaries, manifests, logs, and helper files are intentionally hidden from this view but remain recorded in SQLite/SQL.

Method/k filters retain the selected solution and its shared upstream sources. Candidate-k plot links come from the Step 1 manifest: the combined diagnostic connects to both clustering branches, while the dedicated hierarchical candidate-k plot connects to hierarchical solutions.

The report embeds its graph data and table previews, but figure previews and original-result links use relative paths to files in the run directory. **Keep or share the complete run directory**, preserving its structure, so those links continue to work; copying only the HTML file is insufficient for all previews and results.

## Datasets and availability

Two runnable example matrices and their matching taxonomy table are bundled:

| File | Contents |
|---|---|
| [Example_dataset/binary_matrix.csv](Example_dataset/binary_matrix.csv) | 127 genomes × 227 binary feature columns, plus `Genomes` |
| [Example_dataset/proportional_matrix.tsv](Example_dataset/proportional_matrix.tsv) | 127 genomes × 29 proportional feature columns, plus `Genomes` |
| [Example_taxonomy.csv](Example_taxonomy.csv) | Matching genome-to-phylum annotations |

Use the [quick-start commands](#quick-start) to run these examples. Feature counts above describe the input matrices before cleaning. You can also supply your own compatible matrices.

The manuscript describes six dataset types: targeted gene/pathway presence–absence (DSK_DB), targeted pathway proportions (DSK_P_DB), MAG-level KEGG presence–absence (MAG_KEGG_DB), MAG-level KEGG proportions (MAG_KEGG_P_DB), genome-reconstruction versus KEGG modules (GSMR_KEGG_DB), and PROKKA-derived gene presence–absence (PROKKA_DB).

The bundled matrices are available through the links above. Raw-data accessions, links for the remaining manuscript datasets, and a final data DOI remain to be supplied.

## Benchmarking

MetGuild was benchmarked using the two example datasets distributed with the repository. Each dataset was processed three times using the complete workflow. Runtime is reported as the median wall-clock time across the three runs. Peak memory is the largest maximum resident set size observed across the three runs, and CPU use is the median reported by GNU `time`.

| Dataset                   | Dimensions | Matrix type  | Median runtime | Peak memory | Median CPU | Runs | Status    |
| ------------------------- | ---------- | ------------ | -------------- | ----------- | ---------- | ---- | --------- |
| `binary_matrix.csv`       | 127 × 227  | Binary       | 67.19 s        | 318.5 MiB   | 59%        | 3    | Completed |
| `proportional_matrix.tsv` | 127 × 29   | Proportional | 52.66 s        | 318.8 MiB   | 62%        | 3    | Completed |

Benchmark measurements were collected using GNU `/usr/bin/time -v` on the complete MetGuild workflow.

For the binary matrix:
```typescript
/usr/bin/time -v bash run_metguild_workflow.sh \
  Example_dataset/binary_matrix.csv 15 \
  --matrix-type binary
```

For the proportional matrix:
```typescript
/usr/bin/time -v bash run_metguild_workflow.sh \
  Example_dataset/proportional_matrix.tsv 15 \
  --matrix-type proportion
```

Each command was run three times. The benchmark corresponds to Git commit:

`7f03600adbf8c7ed548fd4423ee92999c2ca7c2a`

The Conda environment, Python version, compute-node hardware information, raw GNU `time` measurements, workflow logs, and exit codes were recorded under `benchmarks/current_release/`.
